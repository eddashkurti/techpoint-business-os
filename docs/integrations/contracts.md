# Integration implementation and operating gates

## WooCommerce read connector

`WooReadClient` uses the official `wp-json/wc/v3` resources over HTTPS and Basic Authorization. It exposes only GET operations for products, variations, orders and refunds. It rejects resource traversal, query credentials, embedded URL credentials, direct IP/localhost targets, nonstandard ports and redirects. `WooSyncService` additionally requires an operator-configured hostname allowlist (`integrations.woocommerce.allowed_hosts`); the default allows only the two TechPoint storefront hostnames. Network policy must prevent access to private networks and DNS rebinding when deployed.

Use a dedicated **Read** Woo key tied to a restricted WordPress user. Store its consumer key, consumer secret and webhook secret as JSON encrypted by Laravel `Crypt::encryptString`; retain the application encryption key securely with independent recovery arrangements. Never expose connection credentials in serialized responses, exception messages or logs. Do not put keys in query strings. Configuring a live key or creating a live webhook is a separately authorized site change.

Collection reads request at most 100 records per page, use `X-WP-TotalPages` when available and otherwise continue until a short page. A page limit prevents an unbounded job. Transient connection failures, HTTP 429 and 5xx receive at most three attempts by default with bounded backoff. Authentication/client errors and redirects fail immediately. A completed reconciliation records success time; a failed one records a sanitized error. Earlier successful snapshots remain available after a partial failure. Snapshot imports are resumable/upserted and do not post financial or stock effects.

`WooSyncService::reconcile(connectionId)` reads products, variable-product variations, orders and refunds into shadow records. Mapping identity is connection + external type + external ID. SKU is search/mapping evidence, not identity. Variation IDs, parent product IDs, order line IDs, payment/status fields and refund/order references remain in source payloads. A new mapping points to its shadow row; an existing reviewed mapping is retained. No import creates an operational ERP sale, changes Woo stock, changes ERP stock, posts revenue or reverses a payment. An approved opening/import policy is required before converting shadow records into operational documents.

Ordinary webhook intake must pass `Request::getContent()` exactly to `WooWebhookVerifier`. It checks base64 HMAC-SHA256 with constant-time comparison before JSON parsing. Accepted bodies enter a durable inbox; their SHA256 body identity prevents reprocessing even when unsigned delivery headers change. The queued `ProcessWooWebhook` fetches authoritative current data rather than applying a possibly stale body. Versioned snapshots refuse a source timestamp older than the stored one. Deletion events are checked against the source; a 404 adds an observed-source-deletion marker while retaining history and without operational reversal. A periodic full read does not infer deletion merely because a record disappears from a changing pagination window.

Woo's initial setup ping differs from normal delivery: its source sends an unsigned form body `webhook_id=<id>` and expects exactly 200. The endpoint may acknowledge only that tiny, strict no-op shape without persisting an inbox event or dispatching work. All data-bearing events still require HMAC. Limit public request size and rate at the web server and application route.

Register `WooReconcileCommand`, schedule `integrations:woo-reconcile` hourly with overlapping execution prevented, and run supervised database queue workers. Event rows retain attempts/error/processed time; failed jobs need monitored retry and reprocessing. Jobs and snapshots may contain personal data, so access and retention follow the financial/customer-data policy. The credentials and customer payload must not appear in public errors.

Primary specifications: [REST v3](https://developer.woocommerce.com/docs/apis/rest-api/v3/), [Read keys / HTTPS Basic authentication](https://developer.woocommerce.com/docs/apis/rest-api/authentication/), [Webhook payload and signature](https://developer.woocommerce.com/docs/apis/rest-api/v3/webhooks/), [Current setup ping implementation](https://raw.githubusercontent.com/woocommerce/woocommerce/trunk/plugins/woocommerce/includes/class-wc-webhook.php).

## Fiscal adapter

Runtime binds `FiscalProvider` to `UnconfiguredFiscalProvider`. It refuses issuance and status operations before any external submission. It has no invented endpoint, certificate, fiscal receipt or success response. A provider replacement requires a certified-product contract, written supported integration boundary, authorized sandbox/production access, correct taxpayer/POS registration and tested physical printing. Fiscal till keys remain on their originating POS under the verified custody model; no unverified central/offshore relocation is implemented.

`FiscalWorkflow::prepare(saleId,payload,operationKey)` freezes the request and deduplicates its stable operation key. Reusing a key for another sale/provider/payload fails. `submit(documentId)` locks and claims only a pending request, persists an attempt, then calls the provider outside the SQL transaction. Real confirmation needs an external reference. A rejection is explicit; a timeout or unexpected post-dispatch exception becomes `outcome_unknown`. Neither submitted nor unknown, confirmed or rejected documents can be blindly submitted again.

`reconcile(documentId)` performs only a provider status lookup for an unresolved submission. It adds an attempt and can resolve confirmation/rejection; an inconclusive answer remains unknown. It never resends. A process crash after the persisted claim leaves the request submitted and blocked until lookup. Posted fiscal requests are corrected through distinct linked requests according to the selected provider's verified rules, rather than editing their frozen payloads. Controller authorization and core-sale linkage remain mandatory.

Fiscal tests use fakes strictly inside the `Tests` namespace. Those fakes prove local transition/deduplication behavior and do not establish live fiscal compatibility or legal issuance. Until a real certified adapter passes external acceptance, required fiscal sale completion must remain guarded. Printed internal order acknowledgments cannot claim fiscal validity.

## Acceptance before live integration

Run local protocol/state tests first, then verify a separately authorized test store and real certified fiscal sandbox: pagination/reconciliation, duplicate and reordered events, bad HMAC, API failure/recovery, a fiscal ambiguous timeout followed by lookup, corrections/partial returns where supported, and a physical 80 mm QR print. Confirm actual costs, keys, device versions, authorization boundaries and legal outage operation before production cutover.
